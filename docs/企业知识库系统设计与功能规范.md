# 1. 系统概述与业务边界

## 1.1 系统定位与业务目标

企业知识库系统是面向企业内部员工的知识沉淀、协同创作与信息共享平台。核心定位如下：

1. **统一知识沉淀**：打破信息孤岛，建立企业级权威知识中心与个人/团队灵活协作的私有知识空间。
2. **轻量高效流转**：采用基于乐观版本比对的直观覆盖策略与灵活审批流，保障协作敏捷性与内容严谨性。
3. **安全合规管控**：提供颗粒度明确的分层分享模型与强管控治理下架机制，所有操作全流程审计留痕且凭据脱敏。
4. **扩展架构友好**：底层数据模型预留语义切片、向量索引与 AI 问答所需的元数据字段，为后续平滑升级 RAG 知识检索奠定基础。

## 1.2 核心业务概念与实体定义

| **实体名称** | **标识符/缩写**     | **说明与业务定位**                                           |
| ------------ | ------------------- | ------------------------------------------------------------ |
| **知识库**   | KB / Knowledge Base | 企业知识的一级组织容器，分为“公共知识库”与“私有知识库”，具备独立的可见性与管理策略。 |
| **分类**     | Category            | 知识库内部的树状目录结构，采用扁平且深度可控的层级体系（最多 2 级），用于文档归类整理。 |
| **文档**     | Document / Doc      | 系统最基础的内容承载单元，正文统一存储为结构化 Markdown。    |
| **草稿**     | Draft               | 针对新建或修改中文档的未发布版本，数据与正式发布文档完全隔离存储。 |
| **快照**     | Snapshot            | 文档正式发布或被覆盖瞬间由系统自动生成的历史镜像，用于安全兜底与版本留存。 |
| **附件**     | Attachment          | 文档挂载的媒体与文件资源，底层物理文件（Blob）与上层业务引用（Ref）彻底解耦。 |

# 2. 统一权限与安全基座（SSOT 全局基准）

## 2.1 全局角色体系与继承关系

系统预置三种全局角色，权限逐级继承： 系统管理员（System Admin） $\supset$ 知识库管理员（KB Admin） $\supset$ 普通用户（General User）。

1. **普通用户**：
   - 浏览与检索公共库所有已发布内容，参与点赞、收藏、评论；
   - **公共库贡献与修改权**：可创建新文档贡献申请，**也可对任意已发布的公共文档创建修改草稿并提交发布审批**；
   - 创建和管理个人的私有知识库；
   - 在被他人分享的私有库/分类/文档范围内行使授权操作。
2. **知识库管理员**：
   - 统一治理所有公共知识库（增删改、分类维护、归档、直接重新上架）；
   - 审批普通用户提交的发布申请（公共区新文档贡献、修改文档上线、跨区划转）。
3. **系统管理员**：
   - 负责全局账号体系、密码治理、角色分配、不可变审计日志检索与系统配置；
   - 保留全站资产的底线安全合规治理特权（合规下架、指定强制转让）。

## 2.2 分层分享与权限模型（未配置即继承，配置即覆盖）

系统不在知识库/分类/文档实体上重复存储分享模式；**以 `permission_overrides` 覆盖标记和 `permissions` 成员记录共同作为权限配置 SSOT**。覆盖标记可独立存在，因此空名单覆盖可明确拒绝访问：

### 2.2.1 继承与覆盖判定规则

1. **未配置状态（自动继承上级）**：
   - 若某分类或文档没有独立覆盖标记（`permission_overrides` 中无节点记录），自动向上继承父级分类的名单与权限；若父分类也未配置，继续回溯根知识库；
2. **配置状态（独立覆盖上级）**：
   - 节点明确选择“覆盖上级”时写入独立覆盖配置；覆盖配置与成员权限记录分开保存，因此即使成员名单为空也能表达明确拒绝；
   - 覆盖状态下，本节点名单与权限级别完全独立，不再沿用上级名单；**空名单表示任何被分享用户都无权访问**（私有库所有者及全局治理角色按各自规则处理）；
   - `inherit` 与 `override` 是显式配置状态：前者恢复继承，后者即使名单为空仍保持覆盖。不得通过“成员表是否有行”推断模式。

### 2.2.2 前端分层分享弹窗（KbShareModal）自闭环交互

- **显式继承选项**：弹窗提供“继承上级”与“覆盖上级”模式选择；继承态显示有效权限摘要但不把继承值写成本节点配置；
- **覆盖态**：选择“覆盖上级”后，成员可为空；对有成员的覆盖配置须选择 reader/editor，空名单表示拒绝所有被分享用户；
- **恢复继承**：选择“继承上级”并保存，删除该节点覆盖标记及成员记录；单纯清空成员名单不会恢复继承，而是保存为空名单覆盖。

### 2.2.3 两种标准分享业务权限

| **分享权限** | **英文标识** | **允许操作范围**                                             |
| ------------ | ------------ | ------------------------------------------------------------ |
| **可阅读**   | reader       | 浏览正文、阅读历史快照、全文搜索检索、预览与下载附件、发表与删除本人评论、点赞、收藏。 |
| **可编辑**   | editor       | 包含 reader 的全部权限；进一步允许在授权范围内创建新文档、编辑正文草稿、上传/移除附件、提交发布申请。 |

# 3. 账号认证与会话管理

- **凭证安全**：用户名/邮箱唯一，密码采用 Argon2id 内存硬散列存储；
- **防暴破**：连续失败 5 次锁定 15 分钟；IP 滑动窗口限流；
- **强制改密**：管理员新建/重置账号标记 must_change_password = true，首次登录强阻断跳转改密；
- **双 Token 体系**：短效 Access Token 仅存前端内存，长效 Refresh Token 存 HttpOnly Cookie；Redis 版本号实现一键全端下线。

------

# 4. 知识库管理

- **公共库 vs 私有库**：公共库全员默认只读，由管理员集体托管，普通用户提交修改需审批；私有库单一所有者终身制/转让制，可自由配置发布审批开关；
- **资产 4 态模型**：published（已发布）、withdrawn（下架治理）、archived（已归档）、trashed（垃圾箱 30 天保护）；
- **容器业务冻结（****is_frozen****）**：独立于资产状态，在跨区划转审批期间对知识库/分类整棵受影响子树冻结写入与移动；不自动改变既有读取权限。提交审批、冻结及解冻均须纳入审计；
- **重新上架双轨制**：公共区管理员免审直接恢复；私有区所有者发起重新上架提审，通过后上线；
- **恢复重名检查**：从垃圾箱恢复知识库时，检查当前作用域的重名状态，同名则引导改名

------

# 5. 目录与分类结构管理

### 5.1 分类树深度与命名规范

- **深度硬约束**：知识库为顶级容器（不计入分类深度）。分类层级**严格最多允许 2 层**（知识库 $\to$ 一级分类 $\to$ 二级分类，总层级深度严格为 3）；
- **同级唯一性**：同一父级节点下分类名称唯一；
- **防循环成环**：移动分类时通过递归 CTE 检验，阻断将节点移动至其子孙分类之下；
- **审批关联清理**：移动某一分类时，**仅取消该被移动分类子树直接相关的待审单据**，绝对不波及全库其他无关单据。

------

# 6. 文档创作、草稿隔离与并发发布

### 6.1 独立草稿管理与 5 秒节流暂存

- 正式文档与草稿彻底隔离存储（documents vs document_drafts）；
- 修改草稿检出时绑定基线版本号 base_version；
- 前端本地采用 **5 秒最大等待节流（maxWait: 5000ms）** 写入 IndexedDB，连续高速打字也不会丢稿；
- **正式文档状态保障**：有人编辑或提审修改草稿期间，线上正式版本状态不因草稿而改变；是否可读、可检索仍由该文档自身生命周期状态及祖先容器状态决定。归档文档不参与检索。
- **草稿身份**：每份草稿有独立 `id` 主键。已有文档的每位编辑者最多保留一份活动草稿；新建文档草稿的 `document_id` 为空，允许同一编辑者创建多份，彼此由草稿 `id` 区分。

### 6.2 乐观并发控制与确认覆盖（解决丢失更新）

- 提交发布时，校验线上 documents.version === draft.base_version：
  - 若一致，原子覆盖并生成快照；
  - 若线上版本已发生递增（他人抢先发布），系统返回 HTTP 409 (40009) 并弹出 Diff 比对卡片；用户审阅后确认覆盖时携带已审阅版本号，再次提交并原子生效，杜绝静默丢失更新。

# 7. 附件管理与标签系统

### 7.1 物理文件（Blob）与业务引用（Ref）解耦

- **存储层与业务层分离**：file_blobs 按 SHA-256 哈希全局去重托管物理文件；attachment_refs 独立记录文档、草稿与快照的业务引用；
- **彻底杜绝裂图**：草稿中删除图片仅删除草稿引用，线上正式文档与历史快照引用完好无损；
- **杀毒四态完备化**：scan_status 严格设为 pending, clean, infected, failed 四态；超时或异常自动转为 failed 并报警阻断下载。

### 7.2 标签系统

- 单文档上限 8 个标签；
- 候选联想词仅聚合公共库已发布标签，严禁刺探私有库词汇；
- 数据库触发器原子维护 tags.ref_count 引用计数。

# 8. 流程编排与审批工作流

- **五类标准审批**：私有库发布提审、公共库新建贡献/已发布文档修改提审、私有资产移入公共区提审、私有资产重新上架提审、跨所有者移动私有资产提审。治理下架与垃圾箱恢复属于有权限角色执行的直接治理操作，不混作审批类型；
- **跨所有者划转规则**：仅支持单篇文档或整棵分类；申请人须具备目标库 editor 权限；强制由目标所有者审批；通过后剥离原私有名单并继承目标库规则；
- **严格反自审原则（No Self-Approval）**：申请人绝不可审批本人提交的单据，数据库约束与应用层双重硬阻断；待审时 `approver_id` 可为空，审批时必须满足 applicant_id <> approver_id；
- **回收站恢复与旧审批**：资产移入垃圾箱时关联待审单据自动标记为 cancelled；资产恢复后**旧审批绝不隐式自动复活**，须由用户确认后重新提交。

------

# 9. 检索发现与互动系统

- **权限前置过滤**：公共库仅搜有效已发布内容，私有库仅搜所有者及有效分享范围内的内容；彻底屏蔽下架、归档与垃圾箱资产。祖先知识库或分类不可用时，其后代不得进入搜索结果；冻结容器中的既有内容仍按原读取权限处理，但不可变更；
- **全字段权重明确**：标题 1.0 > 标签 0.6 > 附件名与作者名 0.4 > 正文 0.2；
- **分布式双重墓碑机制**：Redis 7 天墓碑 + 数据库持久化墓碑表，彻底防止异步消息乱序重放导致已删除数据“幽灵复活”；
- **社交互动持久化**：楼中楼评论体系（comments）、点赞与收藏（user_document_interactions）、最近浏览（user_recent_views，限 20 条）。

------

# 10. 资产生命周期与分级回收站

- **两级垃圾箱**：个人垃圾箱（个人私有库/分类/文档/草稿）与公共垃圾箱（公共资产）；
- **30 天保留与恢复前置检查**：垃圾箱通过软删除和 `deleted_at` 标记实现，保留期内不物理删除；恢复时校验同名冲突；若原父级已删除或移入公共区，要求重新选择合法目的地。到期后才执行受审计的硬删除并写墓碑；数据库外键禁止对仍保留子树执行级联物理删除。

------

# 11. 平台治理与审计中心

- **不可变审计日志**：覆盖所有高危操作，严格执行**密码/Token 敏感凭据脱敏白名单**；正文仅记录版本号与哈希；
- **核心操作同事务落库**：高危治理动作与审计日志在同一数据库事务中原子写入；安全失败事件独立记录；
- **只追加保护与归档特权**：数据库触发器默认阻止 UPDATE/DELETE，支持通过特权会话变量在合规冷备时放行。

# 附录 A：全量数据实体架构速查

### 一、 核心领域实体表（12 张；审计与墓碑支撑表另列）

1. users：账号与全局角色表
2. knowledge_bases：知识库主表（含 is_frozen 容器冻结标记）
3. categories：目录分类表（最多 2 级，depth: 1..2，不设 share_mode 冗余字段）
4. documents：已发布正式文档表（4 态生命周期，不设 share_mode 冗余字段）
5. document_drafts：独立草稿表（含 base_version 乐观基线）
6. document_snapshots：发布前快照历史表
7. file_blobs：物理文件存储表（SHA-256 全局去重，杀毒 4 态）
8. attachment_refs：业务附件引用表（解耦文档/草稿/快照）
9. tags：标签字典表（触发器原子维护 ref_count）
10. document_tags：文档标签关联表
11. permission_overrides / permissions：节点覆盖模式及分层分享成员表（覆盖标记可对应空名单）
12. approvals：审批工作流单据表（硬防自审）

### 二、 通用支撑辅助表（5 张）

1. comments：楼中楼两级评论表
2. user_document_interactions：点赞与收藏轻量关联表
3. user_recent_views：个人最近浏览记录表（每人上限 20 条）
4. notifications：站内系统与审批通知表
5. system_configs：动态业务参数配置字典表

审计与异步索引支撑表：`audit_logs`、`entity_tombstones`。两表不计入上述核心及通用辅助表数量。
