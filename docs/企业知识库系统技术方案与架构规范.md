# 第一篇：全栈 Monorepo 单仓架构

## 1. Monorepo 工程化架构与工作空间规范

### 1.1 单仓架构选型与环境约束

本系统采用轻量可靠的 Monorepo 单仓架构，统一管理前端主应用、后端服务及内部共享库：

- **Node 运行时锁定**：环境锁定为 **Node.js** **>= 22.13.0 LTS**（满足 pnpm 12 原生运行引擎与 ESM 规范）。
- **包管理器**：锁定为 **pnpm@12.10.1**。
  - 在根目录 package.json 声明 "packageManager": "pnpm@12.10.1"；
  - 强制提交 pnpm-lock.yaml，CI/CD 流水线中强制执行 pnpm install --frozen-lockfile，确保构建 100% 可复现；
  - **内容寻址存储（Content-addressable Store）**：基于硬链接机制，杜绝幽灵依赖；
  - **原生脚本调度**：利用原生 pnpm --filter <pkg> 与 pnpm -r run <script> 编排任务。

### 1.2 目录拓扑与工作空间职责划分

enterprise-kb/

```
├── apps/            # 业务应用层（可独立部署实体）
│  ├── web/           # 知识库前端 Web 主应用（Vue 3.5 + Vite 8 + TypeScript 7）
│  └── server/         # 知识库后端 API 服务应用（Node.js 22 LTS + NestJS 12.1.3 + Fastify 5.12.7 + Prisma 7.10.0）
```

### 1.3 跨包引用与依赖规范

- **组织命名空间**：所有内部包统一使用组织前缀 @kb/*。
- **工作区协议引用**：在 apps/web 与 apps/server 的 package.json 中，通过 workspace:* 声明依赖。
- **类型即契约（Single Source of Truth）**：后端实体模型与 API 响应结构在 packages/types 中单点定义，前后端直接引用强类型。

## 3. 网络通信、会话凭证与状态管理

### 3.1 HTTP 标准状态码与 5 位业务 Code 协同规范

- **网络层保留标准 HTTP 状态码**：200 OK、400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、409 Conflict、429 Too Many Requests、500 Internal Server Error；
- **业务层细化 5 位业务 Code**：20000（成功）、40000（参数错误）、40001（Token过期）、40002（强制改密）、40003（无权访问/自审拦截）、40004（不存在）、40009（业务/并发冲突）、40029（限流）、50000（系统异常）；
- **响应头透传**：响应对象顶层透传 headers，支持客户端获取文件名与限流元信息。

### 3.2 Axios 请求与响应拦截器链实现

- HTTP 200 进入成功通道；
- HTTP 4xx/5xx 进入错误通道，针对 status === 401 || code === 40001 触发双 Token 队列并发静默刷新；针对 40002 拦截跳转 /change-password。

#### 4.3.1 组件通信接口与核心逻辑

```vue
// packages/ui/src/components/share/KbShareModal.vue
<template>
<a-modal
         :open="open"
         title="权限与分享设置"
         @ok="handleSave"
         @cancel="$emit('update:open', false)"
         \>
    <!-- 模式显式区分继承与覆盖；空名单是有效覆盖配置 -->
    <a-form-item label="访问模式">
        <a-radio-group v-model:value="form.mode">
            <a-radio value="inherit">继承上级</a-radio>
            <a-radio value="override">覆盖上级</a-radio>
        </a-radio-group>
    </a-form-item>
    <!-- 覆盖名单可为空；有成员时必须选择权限级别 -->
    <a-form-item label="授权权限">
        <a-select
                  v-model:value="form.permission"
                  placeholder="未配置（继承父级，选择后覆盖）"
                  allow-clear
                  \>
            <a-select-option value="reader">可阅读 (reader)</a-select-option>
            <a-select-option value="editor">可编辑 (editor)</a-select-option>
    </a-select>
    </a-form-item>

    <!-- 分享人员可为空；覆盖模式下空名单表示拒绝所有被分享用户 -->
    <a-form-item label="分享成员">
        <a-select
                  v-model:value="form.userIds"
                  mode="multiple"
                  placeholder="未配置（继承父级，选择后覆盖）"
                  allow-clear
                  :filter-option="false"
                  @search="handleSearchUsers"
                  \>
            <a-select-option v-for="user in userOptions" :key="user.id" :value="user.id">
                {{ user.nickname }} ({{ user.username }})
    </a-select-option>
    </a-select>
    </a-form-item>
    </a-modal>
</template>

<script setup lang="ts">
    import { ref, watch } from 'vue';
    import { message } from 'ant-design-vue';
    import { getPermissionsApi, updatePermissionsApi } from '@/api/permission';
    const props = defineProps<{ open: boolean; targetType: 'kb' | 'category' | 'document'; targetId: string }>();
    const emit = defineEmits(['update:open', 'success']);
    const form = ref<{ mode: 'inherit' | 'override'; permission: 'reader' | 'editor' | undefined; userIds: string[] }>({
        mode: 'inherit',
        permission: undefined,
        userIds: [],
    });

    // 打开弹窗拉取当前节点配置
    watch(() => props.open, async (isOpen) => {
        if (isOpen) {
            const { data } = await getPermissionsApi(props.targetType, props.targetId);
            form.value.mode = data.mode;
            form.value.permission = data.permission;
            form.value.userIds = data.userIds;
        }
    });

    // 保存提交逻辑
    async function handleSave() {
        const { permission, userIds } = form.value;
        if (form.value.mode === 'inherit') {
            await updatePermissionsApi(props.targetType, props.targetId, { mode: 'inherit' });
            message.success('已恢复继承上级');
        } else {
            if (userIds.length > 0 && !permission) throw new Error('有分享成员时必须选择权限级别');
            await updatePermissionsApi(props.targetType, props.targetId, { mode: 'override', permission, userIds });
            message.success(userIds.length ? '独立权限已保存' : '已覆盖上级，当前为空名单（拒绝所有被分享用户）');
        }
        emit('update:open', false);
        emit('success');
    }
</script>
```

## 7. 数据库设计与物理表 DDL 规范（无 share_mode 纯净版）

### 7.1 核心设计原则

1. **主键与时区**：UUIDv4 物理主键、TIMESTAMPTZ UTC 时间戳；数据库时间精度由 PostgreSQL 类型精度配置决定，不承诺固定毫秒精度；
2. **纯净继承判定（彻底移除 share_mode）**：分类表与文档表**不设任何 share_mode 字段**。`permission_overrides` 标记是否覆盖，`permissions` 保存覆盖名单；没有覆盖标记即继承，覆盖标记可对应空名单；
3. **物理文件与业务引用解耦（彻底消除裂图）**：file_blobs 按 SHA-256 去重，attachment_refs 独立记录文档/草稿/快照引用；
4. **分类深度严谨约束**：CHECK (depth >= 1 AND depth <= 2)，全系统最多 2 级分类；
5. **杀毒四态完备化**：补齐 failed 状态，定义超时告警门禁；
6. **乐观基线版本（****base_version****）**：独立草稿表中记录检出版本号，解决丢失更新；草稿 `id` 是每份草稿的主键，新建草稿 (`document_id IS NULL`) 可由同一编辑者创建多份。
7. **权限覆盖状态显式化**：`permission_overrides` 有节点行表示覆盖（可无成员行）；没有节点行表示沿父级继承。选择继承时删除覆盖标记，成员记录随外键级联删除。

## 8. 核心鉴权与权限判定引擎规范

### 8.1 节点纯净继承判定（无配置即继承，有配置即覆盖）

```ts
// apps/server/src/modules/permission/permission-traversal.service.ts
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../../database/prisma.service';
import { RedisService } from '../../database/redis.service';
export type EffectivePermission = 'owner' | 'editor' | 'reader' | 'none';

@Injectable()
export class PermissionTraversalService {
    constructor(
    private readonly prisma: PrismaService,
    private readonly redis: RedisService,
    ) {}
    /**
      \* 穿透判定用户对目标文档的最终有效权限
      \* 核心铁律：无配置即继承父级，有配置即独立覆盖
  	*/
    async getDocumentEffectivePermission(userId: string, docId: string): Promise<EffectivePermission> {
        const doc = await this.prisma.document.findUnique({
            where: { id: docId },
            select: {
                id: true,
                kb_id: true,
                parent_id: true,
                status: true,
                knowledge_base: { select: { type: true, owner_id: true, status: true } },
            },
        });
        if (!doc || ['trashed', 'withdrawn'].includes(doc.status)) return 'none';
        // 归档文档不参与搜索；读取权限仍按单独的归档可见性策略判定。
        // 此方法必须检查知识库及完整祖先分类链：任一祖先为 withdrawn/trashed 即拒绝，
        // 任一祖先 archived 时按归档读取策略判定；任何冻结祖先禁止写入/移动，但不自动拒绝读取。
        if (!(await this.hasReadableLifecyclePath(doc))) return 'none';
        
        // 1. 公共库判定：已发布状态对全员开放阅读
        if (doc.knowledge_base.type === 'public') {
            return doc.status === 'published' && doc.knowledge_base.status === 'published' ? 'reader' : 'none';
        }
        
        // 2. 私有库所有者判定：owner 享有绝对自治管理权
        if (doc.knowledge_base.owner_id === userId) {
            return 'owner';
        }
        
        // 3. 第一优先级：查看文档自身是否配置了权限/名单
        const docOverride = await this.prisma.permissionOverride.findUnique({
            where: { target_type_target_id: { target_type: 'document', target_id: docId } },
            include: { permissions: true },
        });
        
        // 文档配置了权限名单 -> 直接以文档配置为准（覆盖），绝不向上回溯！
        if (docOverride?.mode === 'override') {
            const userPerm = docOverride.permissions.find((p) => p.user_id === userId);
            return userPerm ? (userPerm.permission as EffectivePermission) : 'none';
        }
        
        // 4. 第二优先级：文档未配置，递归向上检查分类层级链
        let currentCatId = doc.parent_id;
        while (currentCatId) {
            const catOverride = await this.prisma.permissionOverride.findUnique({
                where: { target_type_target_id: { target_type: 'category', target_id: currentCatId } },
                include: { permissions: true },
            });
            
            // 当前分类配置了权限名单 -> 直接以该分类配置为准（覆盖），阻断向更上层回溯！
            if (catOverride?.mode === 'override') {
                const userPerm = catOverride.permissions.find((p) => p.user_id === userId);
                return userPerm ? (userPerm.permission as EffectivePermission) : 'none';
            }
            
            // 该分类未配置，继续向上回溯父分类
            const cat = await this.prisma.category.findUnique({
                where: { id: currentCatId },
                select: { parent_id: true },
            });
            currentCatId = cat?.parent_id || null;
        }

        // 5. 第三优先级：全部分类均未配置，回溯查看根知识库配置
        const kbOverride = await this.prisma.permissionOverride.findUnique({
            where: { target_type_target_id: { target_type: 'kb', target_id: doc.kb_id } },
            include: { permissions: true },
        });
        if (kbOverride?.mode === 'override') {
            const userPerm = kbOverride.permissions.find((p) => p.user_id === userId);
            return userPerm ? (userPerm.permission as EffectivePermission) : 'none';
        }
        
        // 6. 全链路未配置任何分享名单，且当前用户非所有者，默认无权访问
        return 'none';
    }
}
```

- **Redis 版本号即时失效协议**：
  - 授权变更事务将失效事件写入 outbox，提交后对目标及相关祖先/后代权限缓存递增版本；继承链变更必须使受影响后代缓存失效。Redis INCR 不属于数据库事务，不能宣称跨 Redis/数据库原子提交；
  - 缓存键拼接版本号：perm:{targetType}:{targetId}:{userId}:{targetPermVersion}，彻底杜绝权限残留。

## 9. 状态机流转与并发版本控制规范

### 9.1 状态机与业务冻结彻底解耦

- 正式文档 4 态：published, withdrawn, archived, trashed；草稿提审不改变线上版本状态。归档、下架、垃圾箱内容均不检索；公开读取及私有授权均须先通过知识库和祖先分类的状态门禁；冻结只阻断写入和移动，不自动改变既有读取权限；
- 容器业务冻结通过 is_frozen = true 独立标记。

### 9.2 乐观并发基线（CAS）与确认覆盖

- 提交发布时比对 documents.version === draft.base_version；冲突时返回 HTTP 409，展示 Diff 比对，确认覆盖需携带 confirmed_overwrite_version，原子生效并固化快照。

### 9.3 跨所有者移动规则

- 仅支持单篇文档或整棵分类；操作人须具备目标库 editor 权限；审批表 `destination_kb_id` 记录目标库，目标所有者为唯一审批人；通过后剥离原私有名单并继承目标库规则。

### 9.4 目录移动防成环与审批清理

- PostgreSQL 递归 CTE 阻断成环；移动分类时**仅取消该被移动子树相关的待审单据**，不波及全库其他无关单据。

## 10. 文件对象存储与安全下载流规范

- **10.1 物理与业务解耦**：物理文件写入 file_blobs，业务关联写入 attachment_refs。草稿删图仅删除业务引用，线上正式文档与历史快照绝对零裂图；
- **10.2 杀毒四态与异常门禁**：scan_status 严格设为 pending, clean, infected, failed 四态；超时（60s）或服务异常自动流转为 failed 并报警阻断下载；
- **10.3 代理流式下载**：GET /api/v1/attachments/:id/download 动态鉴权，使用 @BypassTransform() 豁免 JSON 包装；支持 Range 请求头返回 HTTP 206 断点续传，RFC 5987 防乱码标头；
- **10.4 孤立文件回收**：定时任务清理 file_blobs 前，必须确认其在 attachment_refs 中被引用总数为 0。

## 11. 全文检索与向量索引预留规范

- **11.1 全文检索与权重**：PostgreSQL 16+ tsvector + GIN + pg_trgm 检索；标题 1.0 > 标签 0.6 > 附件名与作者名 0.4 > 正文 0.2；只检索生命周期有效且具备访问权限的 published 文档，withdrawn、archived、trashed 文档一律不进入索引/结果；祖先知识库或分类不可用时同步排除后代；冻结只阻断写入与移动，不自动改变既有读取权限；
- **11.2 分布式双重墓碑机制**：Redis 7 天墓碑 + 数据库 entity_tombstones (entity_type, entity_id, purged_at) 表，彻底杜绝数据幽灵复活；
- **11.3 语义切片与向量索引预留**：Markdown H1-H3 语义切片（每块 500–800 tokens，重叠 100 tokens），分块绑定主文档元信息实现具备权限感知的 Permission-Aware RAG；PostgreSQL 预留 pgvector 扩展。索引及召回复用同一生命周期与权限过滤，归档文档不生成可检索向量。

## 12. 不可变审计日志、系统监控与数据备份规范

### 12.1 审计日志脱敏与事务可靠落库

- AuditInterceptor 强制过滤密码、Token 等敏感字段为 [PROTECTED]；正文仅记录版本号与哈希；
- 核心管理动作与审计日志在同一数据库事务中原子写入；安全失败事件独立记录。

### 12.2 系统全链路监控与可观测性（Prometheus + Grafana + TraceID）

- 暴露 /metrics 监控 QPS、P99 延迟、错误率、EventLoop 延迟与连接池；全链路贯通全局唯一 X-Trace-Id。

### 12.3 容灾、数据备份与业务恢复（RPO < 5 分钟闭环）

- 同城同步物理流复制可在同步提交与故障切换策略满足条件时实现零数据丢失；RTO < 30 秒须通过演练验证；
- `archive_timeout = 300` 仅促使 WAL 段定期切换，不单独构成 RPO 保证。异地 RPO < 5 分钟还依赖 WAL 归档/传输成功、接收端持久化确认、延迟监控与故障告警；将这些监控及恢复演练作为达标条件；
- 每日全量备份 + PITR 秒级回滚；S3 跨区域双活同步，RTO < 30 分钟。
